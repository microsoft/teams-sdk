## Streaming

You may also stream messages to the user which can be useful for long messages, or AI generated messages. The SDK makes this simple for you by providing a `stream` function which you can use to send messages in chunks.

Streaming changes how the response arrives, not how fast your agent produces it. Text appears incrementally as it is generated, so the user sees progress rather than a blank screen, and you can show a thinking or status indicator before any real output exists. A streamed response is also stoppable: when the user stops it, the SDK surfaces the cancellation to your handler so you can abandon the remaining work. The gain is in perceived time to first output, which is why streaming suits long or model generated replies and adds little to a short one you could simply send.

<LanguageInclude section="streaming-example" />

:::note
Streaming is currently only supported in 1:1 conversations, not group chats or channels. Teams also supports only one concurrent streaming response per chat at a time.

Every inbound activity gets its own stream, and the SDK closes that stream at the end of the turn. It does not serialize turns, though, and handlers can run concurrently, so a second activity can arrive while the first is still streaming. Streaming therefore brings message handling concurrency concerns that do not exist when you just send a reply, and resolving them may be implemented in your custom code by serializing turns per conversation or by finalizing the in-flight stream before starting the next one.
:::

### Chunk pacing and retries

You do not need to throttle your own chunks. Rapid <LanguageInclude content={{"typescript": "`stream.emit()`", "python": "`ctx.stream.emit()`", "csharp": "`writer.AppendResponseAsync()`"}} /> calls are coalesced and spaced roughly 500 milliseconds apart, so a token-by-token loop becomes a couple of network calls per second rather than one call per token. Every streamed chunk carries the full text accumulated so far rather than just the newest delta, so collapsing several chunks into one send never loses content. Wrapping your own throttle or sleep around each chunk mostly slows the response down, since it would be pacing a path that is already paced.

<LanguageInclude section="streaming-pacing-details" />

None of this extends the [two minute window](#the-two-minute-streaming-limit), which runs on wall clock from the first chunk. Pacing keeps a stream under the streaming API's rate limit, but does not buy more time. It also applies only to the streaming path: the plain activity updates go out exactly when they are sent, so that cadence stays yours to manage.

### The two minute streaming limit

Teams keeps a message stream open for two minutes, measured from its first chunk. After that the service rejects further chunks for that message with a `403` and the [error code](https://learn.microsoft.com/en-us/microsoftteams/platform/bots/streaming-ux#error-codes) `ContentStreamNotAllowed` (`Content stream finished due to exceeded streaming time.`).

However, hitting the limit does not mean the response is lost. The SDK marks the stream as timed out and stops pushing chunks, but it keeps buffering everything your agent produces, and <LanguageInclude content={{"typescript": "`stream.close()`", "python": "`ctx.stream.close()`", "csharp": "`writer.FinalizeResponseAsync()`"}} /> finalizes by updating the original message in place with the full buffered text. 

:::warning
The two minute clock starts on the **first streamed chunk**, and an informative update (<LanguageInclude content={{"typescript": "`stream.update()`", "python": "`ctx.stream.update()`", "csharp": "`writer.SendInformativeUpdateAsync()`"}} />) is a chunk. An agent that posts a status update immediately and then thinks for three minutes has spent its entire window before emitting a single token. When the slow work happens before you have any output, do that work first and open the stream once real content starts.
:::

### Running longer than two minutes

To outlast the window, hand off before it closes: stream normally, then finalize the stream and continue the response growing with plain activity updates. No streaming window applies to plain updates, so the answer can keep arriving for as long as your agent runs.

<LanguageInclude section="streaming-handoff-example" />

Plain updates are subject to ordinary activity throttling rather than the streaming path's allowance, so pace them at a cadence measured in seconds rather than sending one per token.

### Starting another streamed message

Calling <LanguageInclude content={{"typescript": "`stream.emit()`", "python": "`ctx.stream.emit()`", "csharp": "`writer.AppendResponseAsync()`"}} /> again after the stream has been closed posts a second, separate message in the conversation by reusing the SDK object in your custom handler; it clears its buffered state and starts the new message. The second message gets its own stream id, so it also gets its own fresh two minute window. The message already finalized stays finalized and is not reopened or extended. Use this when your agent has a genuinely separate second answer to stream, not as a way to give one response more time.

### Streaming in threads

The first message of a stream is placed the same way as a response sent with <LanguageInclude section="context-send-method-name" />.
See [Reactive Threading](#reactive-threading-within-a-handler) for the rules.
In a 1:1 chat the stream starts in the thread when the inbound message is inside a thread, and at the top level otherwise.
The SDK applies the same rules in channels: a channel stream starts in the thread of the inbound message.
Without `channelData.replyChain.id` on the inbound activity, the stream is not placed in a reply chain.
Teams itself supports streaming only in 1:1 chats, as noted above.

Only the first chunk of each streamed message uses the reply chain route.
The later chunks are sent to the inbound conversation with the stream id of the first message.
In a 1:1 chat inside a thread, the streamed message appears in the thread pane (checked live with TypeScript and Python).
In a channel, if the service answers 404 to the reply chain route, the first chunk is posted to the same thread through the legacy channel threading endpoint, as with <LanguageInclude section="context-send-method-name" />.
In a 1:1 chat, a failed reply chain route does not fall back.

## Targeted Messages

Targeted messages, also known as ephemeral messages, are delivered to a specific user in a shared conversation. From a single user's perspective, they appear as regular inline messages in a conversation. Other participants won't see these messages, making them useful for authentication flows, help or error responses, personal reminders, or sharing contextual information without cluttering the group conversation.

To send a targeted message when responding to an incoming activity, use the <LanguageInclude section="targeted-method-name" /> method with the recipient account and set the targeting flag to true.

## Threading

In Teams channels and chats, the SDK can send messages into reply chains (threads).
The SDK provides helpers to simplify working with threads.

In this guide, top-level means a message in the main chat or channel conversation, and in-thread means a message in a reply chain (thread).

### Reply modes

:::info[Version 2.3]
Reply modes are available starting in version 2.3.0. Before 2.3.0, a reply always matched the level of the inbound message, which is the <LanguageInclude content={{"typescript": "`quote`", "python": "`quote`", "csharp": "`ReplyMode.Quote`"}} /> mode.
:::

The reply mode decides where <LanguageInclude content={{"typescript": "`context.reply()`", "python": "`ctx.reply()`", "csharp": "`context.ReplyAsync()`"}} /> places its response in a chat, and whether it quotes the inbound message.
Set it for the whole app, or pass it on a single call, which overrides the app setting.

<LanguageInclude section="reply-modes-example" />

In a channel every reply goes in the thread of the inbound message, so the mode only decides the quote.
The mode affects only <LanguageInclude content={{"typescript": "`context.reply()`", "python": "`ctx.reply()`", "csharp": "`context.ReplyAsync()`"}} />. It does not change <LanguageInclude content={{"typescript": "`context.send()`", "python": "`ctx.send()`", "csharp": "`context.SendAsync()`"}} />, quoting a specific message, streams, plans or proactive messages.

:::note[Replies that cannot be threaded]
When the inbound activity lacks the ids threading needs (see [Where messages land](#where-messages-land)), e.g. in a meeting, a reply is never threaded, so it keeps the quote in every mode, including <LanguageInclude content={{"typescript": "`thread`", "python": "`thread`", "csharp": "`ReplyMode.Thread`"}} />.
Without a thread, the quote is what shows which message the reply answers.
:::

### Where messages land

Where a message lands depends on the method and the scope:

| Method | Chat | Channel |
|---|---|---|
| <LanguageInclude content={{"typescript": "`context.send()`", "python": "`ctx.send()`", "csharp": "`context.SendAsync()`"}} /> | Matches level of user's message | In-thread |
| <LanguageInclude content={{"typescript": "`context.reply()`", "python": "`ctx.reply()`", "csharp": "`context.ReplyAsync()`"}} /> | Starts a thread under a top-level message, or stays in the existing thread (default [reply mode](#reply-modes)) | In-thread |

Threading needs `channelData.replyChain.id` on the inbound activity, plus `channelData.chat.id` in a chat or `channelData.channel.id` in a channel.
Without them (e.g. in a meeting), the SDK sends to the same conversation the inbound activity came from.
In a channel, that conversation can still be the thread of the inbound message.

To send a top-level message while handling a message in a thread, or to reply in a thread without an inbound activity (e.g. when a long task finishes), see [Proactive Messaging](./proactive-messaging#proactive-threading).

### Reactive Threading Within a Handler

Use <LanguageInclude section="context-send-method-name" /> to send reactively without quoting, or <LanguageInclude section="context-reply-method-name" /> to send a reactive reply that quotes the inbound message by default.
The table in [Where messages land](#where-messages-land) shows where each one goes.

<LanguageInclude section="threading-reactive-example" />

A thread starts under the message the inbound activity is about: the user's message, or the message the user reacted to, edited, deleted or clicked a card on.
A reply to a deleted message still starts a thread under it, which Teams shows as "This message has been deleted."
If that message cannot be a thread root (e.g. a card button message whose id is not a message id), the reply stays at the top level.
When the service rejects a thread reply in a chat, the error is thrown to your handler and the reply is not sent at the top level instead.

Because the reply starts a thread and <LanguageInclude content={{"typescript": "`context.send()`", "python": "`ctx.send()`", "csharp": "`context.SendAsync()`"}} /> does not, a handler that replies and then sends at the top level splits its answer between the thread and the main conversation.
To keep follow-ups in the thread, send them with <LanguageInclude content={{"typescript": "`context.reply()`", "python": "`ctx.reply()`", "csharp": "`context.ReplyAsync()`"}} /> as well, using the <LanguageInclude content={{"typescript": "`thread`", "python": "`thread`", "csharp": "`ReplyMode.Thread`"}} /> mode if they should not quote again.

A typing indicator is placed like a message: when the inbound activity is inside a thread, the indicator shows in that thread.
A typing indicator never starts a new thread, so for a top-level message the indicator shows in the main conversation while a reply that starts a thread appears in the thread.

### How the SDK chooses the destination

#### Where the SDK takes the destination from

The SDK reads `channelData` on the inbound activity to find the destination and does not parse the conversation id.
To tell a channel from a chat, it also uses `conversation.conversationType`: `channel` selects the channel rules below, and anything else selects the chat rules.

- **Channel:** a response to a `message` is sent through the reply chain `channelData.replyChain.id` of the channel `channelData.channel.id`.
  If the reply chain route answers HTTP `404`, the SDK posts to the same thread through the legacy channel threading endpoint instead.
  The SDK checks only the status code.
- **Chat:** when the inbound activity is inside a thread (see the table below), the response is sent through the reply chain `channelData.replyChain.id` of the chat `channelData.chat.id`.
  Otherwise <LanguageInclude content={{"typescript": "`context.send()`", "python": "`ctx.send()`", "csharp": "`context.SendAsync()`"}} /> sends to the inbound conversation, at the top level, and <LanguageInclude content={{"typescript": "`context.reply()`", "python": "`ctx.reply()`", "csharp": "`context.ReplyAsync()`"}} /> starts a thread through the reply chain of the message the activity is about, unless the reply mode keeps it at the top level or that message cannot be a thread root.
  An error from the reply chain route is thrown to your handler, and the response is not sent anywhere else.

#### Responding to edits, reactions and card actions

In a chat the SDK also places a response to an inbound activity that is not a typed message.
It compares `channelData.replyChain.id` with the id of the message the activity acts on, and the activity is inside a thread when they differ.

| Inbound activity | Message it acts on | Inside a thread when |
|---|---|---|
| `message` typed by the user | The message, `activity.id` | `replyChain.id` differs from `activity.id` |
| `messageUpdate`, `messageDelete` | The edited or deleted message, `activity.id` | `replyChain.id` differs from `activity.id` |
| `messageReaction` | The reacted message, `replyToId` | `replyToId` is a plain number other than `0` that differs from `replyChain.id` |
| `message` with `channelData.source`, sent by a card button (`messageBack`, `Action.Submit`) | The message with the card, `replyToId` | `replyToId` is a plain number other than `0` that differs from `replyChain.id` |
| `invoke` with `value.messagePayload` (a message action) | The message the action ran on, `value.messagePayload.id` | That id is a plain number other than `0` that differs from `replyChain.id` |
| Any other `invoke` with a `replyToId`, such as `adaptiveCard/action` from `Action.Execute`, `task/fetch` and `task/submit` from a card button, or `message/submitAction` feedback | The message with the card or feedback buttons, `replyToId` | `replyToId` is a plain number other than `0` that differs from `replyChain.id` |
| `invoke` with neither, such as a compose box action or sign-in | None | `replyChain.id` is present |
| Any other activity, such as `installationUpdate` or `conversationUpdate` | None | Never |

So a response to a card button clicked on a card inside a thread is sent into that thread.
For a card on a top-level message, <LanguageInclude content={{"typescript": "`context.send()`", "python": "`ctx.send()`", "csharp": "`context.SendAsync()`"}} /> answers at the top level, and <LanguageInclude content={{"typescript": "`context.reply()`", "python": "`ctx.reply()`", "csharp": "`context.ReplyAsync()`"}} /> starts a thread under the card unless the reply mode is <LanguageInclude content={{"typescript": "`quote`", "python": "`quote`", "csharp": "`ReplyMode.Quote`"}} />.
A reply to a reaction quotes the message the user reacted to, unless the reply mode leaves the quote out.
A `replyToId` that is not a plain number, such as an encrypted id, is never inside a thread.

The SDK uses `conversation.conversationType` only to tell a channel from a chat.
In a chat it does not require a particular type to place a response.
In the 1:1 chat of an agentic user, card button clicks (`messageBack`, `Action.Submit`, `Action.Execute`) and the `task/fetch` and `task/submit` invokes they open have arrived with `conversationType` set to `groupChat`, a service issue that is being corrected.
The SDK places the response to them from `channelData` like any other activity, so a response to a click inside a thread is sent into that thread.

In a channel only a `message` is placed, and a card button click that arrives as a `message` is placed like any other.
The SDK sends a response to any other activity in a channel to the inbound conversation.

For proactive threading (sending to a thread outside of a handler), see [Proactive Messaging](./proactive-messaging#proactive-threading).

## Quoted Replies

Quoted replies let your agent reference a previous message in the conversation. When a user sends a message that quotes another message, your agent receives structured metadata about the quoted content. Your agent can also send messages that quote previous messages.

### Receiving Quoted Replies

When a user quotes a message and sends it to your agent, the quoted reply metadata is available on the inbound activity. Use the <LanguageInclude content={{"csharp": "`GetQuotedMessages()`", "typescript": "`getQuotedMessages()`", "python": "`get_quoted_messages()`"}} /> method to access all quoted reply entities.

<LanguageInclude section="quoted-replies-receive-example" />

Each quoted reply entity contains the quoted message's ID, sender information, a preview of the quoted text, and whether the quoted message has been deleted.

### Sending a Quoted Reply

When your agent calls <LanguageInclude content={{"csharp": "`ReplyAsync()`", "typescript": "`reply()`", "python": "`reply()`"}} />, the SDK automatically stamps a quoted reply entity referencing the inbound activity. The reply will appear as a quoted reply in Teams.

The reply quotes the inbound activity only when that activity can be quoted, so a reply to a card action or another invoke is sent without a quote.
A reply to a reaction quotes the message the user reacted to.
The [reply mode](#reply-modes) decides whether the quote is added: <LanguageInclude content={{"typescript": "`thread`", "python": "`thread`", "csharp": "`ReplyMode.Thread`"}} /> mode leaves it out, except on a reply that cannot be threaded (see [Reply modes](#reply-modes)).
To quote in a card or invoke handler, quote the message that holds the card with <LanguageInclude content={{"csharp": "`QuoteAsync()`", "typescript": "`quote()`", "python": "`quote()`"}} /> and its `replyToId`.

<LanguageInclude section="quoted-replies-reply-example" />

To quote a different message in the same conversation (not the inbound message), use the <LanguageInclude content={{"csharp": "`QuoteAsync()`", "typescript": "`quote()`", "python": "`quote()`"}} /> method with the message ID you want to quote.

<LanguageInclude section="quoted-replies-quote-reply-example" />
